# CS Works ファイル保持・手動削除 — 一括リリース判定

更新日: 2026-10-25

## 目的
30日経過した対象ファイルについて、管理者が明示的に選択・確認して手動削除する。自動削除は対象外。顧客ファイルを試験で削除しない。

## 実装済み・画面検証済み
- 管理者用の保持対象一覧と削除候補の読み取り専用プラン
- 個別ファイルの手動削除事前照合（読み取り専用）
- テスト専用の固定ファイルについて、識別、Storage内容、共有リンク、保留状態、ジョブの照合
- テスト専用の中断状態診断（claimed / storage_removed / Storageの有無）
- テスト専用の確認文字列・模擬確認ダイアログ
- Vercelの専用削除フラグが無効であることの読み取り専用確認
- Supabaseの専用DB最終整理関数の登録・権限確認

## 未検証・リリース阻止条件
1. テスト用Storage削除APIは、削除後にStorageオブジェクトの不存在を独立検証していない。
2. Storage削除後、ジョブをstorage_removedに更新する前に通信・DB更新が失敗した場合、claimedのまま残る。診断はあるが、手動復旧手順の実地確認は未完了。
3. 同時実行を防ぐ原子的な実行取得（ロック）を、Storage削除API内では確立していない。事前照合と削除の間の競合対策が必要。
4. 本番用の個別手動削除実行APIと管理者の最終確認フローは未完成。読み取り専用preflightを本番削除実行と混同しない。
5. 実削除後のDB最終整理、履歴保存、再実行防止のエンドツーエンド検証が未完了。
6. 保留・共有リンク・ファイル種別・30日経過条件について、実行直前にも一貫した再判定が必要。

## まとめて進める残作業
A. 実行APIに原子的な実行取得、削除後のStorage不存在確認、失敗時の明示的な状態記録を追加する。
B. 専用テストファイルだけを対象に、Storage削除→状態診断→DB最終整理→履歴確認を段階的に検証する。
C. 同じ安全条件を本番用の30日経過ファイルの手動削除APIに適用し、管理者の明示的な操作に限定する。
D. 例外系（共有リンク・保留・対象外種別・重複パス・二重実行）を検証してから公開判定する。
