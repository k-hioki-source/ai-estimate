# CS Works ファイル保管：手動削除運用設計

## 運用方針
- 案件完了から30日後を削除候補日とする。7日前から管理者向けに確認対象を表示する。
- 当面は管理者の手動承認方式。自動削除は無効のままにする。
- 削除対象は review / revision / delivery のみ。顧客アップロード・請求書などは対象外。
- 削除保留中の案件は削除しない。

## 削除前の必須確認
1. 認証済み管理者であること。
2. 案件が完了済みで、完了から30日以上経過していること。
3. 対象ファイルが案件に属し、アップロード日時・Storageパス・種類が適正であること。
4. 保留状態の照会に成功し、保留されていないこと。
5. Storageオブジェクトが存在し、パス参照が一意であること。
6. 有効な共有リンクが存在せず、照会エラーもないこと。
7. 競合する削除ジョブが存在しないこと。
8. 管理者に案件・ファイル名・件数を再提示し、明示的に最終確認を得ること。
9. 確認画面の結果を信頼せず、削除実行API内で条件を再照合すること。

## 実行・障害対応（実装前の設計）
- 削除処理は一意のジョブを取得してから開始する。複数回のクリック・同時実行を防ぐ。
- Storage削除の成否を確認してからDB記録を整理する。削除履歴を残す。
- Storage削除後にDB整理が失敗した場合は、ジョブ状態を保持し、管理者による照合・復旧が可能な状態にする。
- Storageの不在だけで削除成功と断定しない。ジョブと対象ID、削除履歴を照合する。
- 不明な状態は安全側に停止し、自動的に削除を再試行しない。
- 既存の復旧テスト用データは専用の片付け手順が確定するまで保持する。

## 本番公開前の検証
- 30日未経過、保留、対象外種類、共有リンク有効、重複パス、ジョブ競合の拒否
- 正常削除、二重実行防止、Storage削除後のDB障害、履歴記録失敗、復旧処理
- 隔離されたテスト用データだけで実削除を検証し、実案件には使用しない
- 手動削除の安全性を確認してから管理者画面の実行ボタンを有効にする
- 自動削除への移行は別途判断し、明示的な承認なしに有効化しない

現時点では、削除前チェックAPIは読み取り専用であり、手動削除実行APIは未実装。
