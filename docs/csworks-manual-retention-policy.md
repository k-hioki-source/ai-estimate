# CS Works 保管見直し・個別削除の運用

2026-10-26 合意仕様。既存の削除実装設計・リリース判定書より本仕様を優先する。

## 公開対象
- 顧客・管理者の画像/PDFプレビュー。
- 7日期限の共有リンク発行・期限前の無効化。
- 完了から30日を保管見直し日とする管理者一覧。7日前から表示する。
- 対象は review / revision / delivery。reference等の顧客支給資料は対象外。
- 保留設定は維持。30日経過で必ず削除する約束ではない。
- 期限後削除は管理者がSupabaseで個別対応。サイト内の期限後削除・自動削除・定期通知は提供しない。
- 既存の顧客による制作資料削除や支払リマインダーは別機能として維持。

## 個別対応の手順（この文書自体は削除を許可しない）
1. 対象案件、完了日、ファイル種類、保留、顧客との保存合意を確認する。
2. 管理者一覧は最大200案件。全件一覧ではない。実行直前にSupabaseでも対象を確認する。
3. 対象のfile ID / project ID / bucket / storage_pathを照合する。名前だけで判断しない。
4. 復元可能なファイルのバックアップと関連DB記録を確保し、復元方法を確認する。
5. 有効な共有リンクや重複Storageパス参照、既存削除ジョブがあれば止めて調査する。
6. StorageとDBは一括トランザクションではない。固定対象1件ずつ扱い、Storageの削除後の不存在を確認してから対応するDB記録を整理する。
7. エラー・結果不明なら再実行せず、その時点のStorage/DB状態を調査する。削除済みを推測して記録を消さない。
8. 対象・確認者・日時・バックアップ先・結果・残存する共有参照/ジョブを別途記録する。Supabaseの手作業はサイトの削除履歴へ自動記録されない。

## 実装上の境界
- 削除テスト終了に伴い、変更を行う12個のテスト用APIは全環境で403に固定。既存の確認文字列・固定ID・過去の検証コードは保持する。
- `/admin/file-retention/tests` は404。UI非表示とは別にAPI自体を停止する。
- 保存期限Cronのスケジュールを除外し、残る通知コードも送信を無効化。支払期限Cronは維持する。
- 既存マイグレーションは書き換えず、DB設定・デプロイ・実データ操作は行わない。
- Productionへの適用には別途承認と、環境変数・RLS・DB・通常機能の受け入れ確認が必要。

## main基点の公開候補での扱い
上記の12テストAPI停止はレビュー用ブランチの安全措置。release/csworks-preview-manual-retention-20261026では過去のテストAPI・テスト画面・保管Cron・新規migration群自体を含めず、公開用5 APIのみを選別する。DB/Storageの手動削除運用と公開前の承認条件は同じ。
